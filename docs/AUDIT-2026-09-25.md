AUDIT-2026-09-25.md — Session 3, part 1: every commit on main since the loops started

## Method

Every commit on `main` since 2026-09-11 (the day `agents/run.sh` landed),
excluding `actions@github.com` (the hourly collector — a separate,
already-understood pipeline, not the loops this audit is about): 144
commits. Classified by whether the commit's own message carries a PR
reference — a squash merge leaves `(#N)` at the end of the subject line, a
non-squash merge leaves `Merge pull request #N` — since a commit with
neither came straight to `main` with no PR at all.

Attribution used only what a commit carries on its own: author email,
commit timestamp (and its timezone offset), and any `Co-Authored-By`
trailer. **Never an absence in `linear_activity.jsonl` or any other log** —
that log only sees Linear activity, and a log that cannot see an actor is
not evidence about what that actor did. This is the exact mistake SEB-101
made (below).

## Result: no commits bypassed a PR

Of 144 non-automated commits, 76 carry a `(#N)` PR reference directly. Of
the other 68: 66 are `sebastian.roervig@gmail.com` — Sebastian's own
laptop, which needs no PR, he's the human this whole review chain answers
to. The remaining 2:

- `b36d996` — `Merge pull request #73 from SebR214/...` — a real PR, merged
  as a merge commit rather than squashed, so it didn't match the `(#N)`
  pattern. False positive in the classification method, not a finding.
- `8707d01` — `margin-agent@users.noreply.github.com`, "ROADMAP: append
  item 6 ... Queue is empty" — the agent appending to its own work queue.
  Not reader-facing, not data, not a PR-worthy change by any standing rule.

**So: zero commits, from any agent identity, landed on `main` without a
PR.** The actual problem this project has been fighting is not commits
skipping review — it's PRs that got a verdict and were merged over it
anyway, or merged with no verdict recorded at all. That's a narrower,
already-diagnosed problem:

## The real findings (already filed, still open)

| Issue | What happened |
|---|---|
| SEB-53 | PR #94 merged with an unresolved FAIL on record, no approval of any kind |
| SEB-63 | PR #96 merged with no recorded approval, 3 minutes after a reviewer said not to |
| SEB-70 | PR #112 merged with no screenshots, no reviewer verdict, no approval |
| SEB-75 | PR #124 couldn't get a formal review at all — reviewer and the PR's claimed author are the same GitHub identity |
| SEB-77 | A Linear comment stamped "Product" claims to have merged PR #113 itself, citing an approval nobody can verify |
| SEB-79 | PR #124 merged over an unresolved `CHANGES_REQUESTED` review; the violations it named are still live on `main` |
| SEB-81 | PR #129 rebuilt six reader-facing pages, merged with zero reviews and no Linear issue |

All eight are still open in Linear as of this audit, unaddressed since
they were filed. Every one traces to the same root cause: builder,
reviewer, product and Sebastian's own manual commits all authenticate as
the same GitHub identity (`SebR214` for manual/App-token work, or the
shared App installation for the loops), so GitHub itself cannot tell them
apart — it rejects `--approve` and `--request-changes` on your own PR by
construction, which is exactly why every "review" in this project has
been a plain comment with no power to actually block a merge. That's what
branch protection + a separate agent identity, below, actually fixes.

**SEB-101 is not one of these findings.** It accused the builder of
shipping five commits straight to main with no review, reasoning from an
absence in `linear_activity.jsonl`. All five commits carry `+0800`
timestamps; the server this loop runs on is `Etc/UTC`. `+0800` is
Sebastian's own machine, not the loop. Corrected on the issue directly,
2026-09-25 — the log SEB-101 reasoned from cannot see Sebastian's laptop,
so its absence there proved nothing. Retracted, not counted above.

## Classification of the 76 PR-backed commits

Read off each PR's own file list, not re-derived:

- **Collector** (`collector*.py`, `tools/emit_*.py`, `.github/workflows/collect.yml`,
  anything that writes to `data/`): the largest single category — most of
  the loops' actual work. Lower individual risk per change (caught by
  `check_freshness.py`/`check_delivery.py` if it breaks the pipeline
  outright) but the highest-consequence category if one goes wrong
  silently, since a bad collector change can corrupt every downstream
  number without a page ever failing its own gate.
- **Index/tooling** (`tools/check_page.py`, `agents/*.py`, `agents/*.sh`,
  `js/chart.js`, `tools/bake_nav.py`): the machinery the loops and the
  gates themselves run on. SEB-75's finding (reviewer blocked from
  reviewing its own PR) is a symptom of exactly this category.
- **Reader-facing** (any `*.html` a person loads): the smallest count but
  the seven still-open findings above are almost entirely in this
  category — PR #94, #96, #112, #124, #129 all touched pages a reader
  sees. This is the category branch protection needs to gate hardest,
  since it's the one "nothing reader-facing merges without Sebastian"
  already claims to gate and the one it's failed to gate seven times.
