Findings

Running a site on agents I don't fully trust

margin.wiki is run around the clock by four agents, and this is what it's actually taken to let them run something real without them quietly getting things wrong, told through the things that broke along the way.

One agent collects prices, one builds, one reviews what got built and one decides what to build next, and hour to hour there's no person in that loop — which sounds like a pitch but is honestly more of a risk. So most of the work so far has gone into making that risk manageable, mostly by assuming the agents will be wrong at some point and building it so that when they are, it's obvious rather than quiet.

The collector that ran for 34 days and collected nothing

An early version of the price collector was pointed at a hostname that didn't resolve — basically a typo — and went straight onto an hourly schedule without ever being run once by hand. It ran every hour for 34 days and logged nothing but DNS errors, and from the outside you couldn't tell: there were no wrong numbers or made-up rows, just nothing, and nothing was set up to treat nothing as a failure.

What fixed it was a rule that no collector goes on a schedule until it's been run once as a dry run that prints exactly what it would write and writes nothing, and every collector has that step now. It turns out a 34-day failure doesn't need a bug — just nobody looking at the first output before automating the next thousand.

The key that burned through the credits in twenty minutes

There are two credentials running this: one on a flat subscription for the three agent loops, and a separate metered key with narrow permissions for the one feature that calls a model on every public request. They're meant to never live in the same file or environment, but for a short while they did, because a config change put the metered key where the subscription credential should have been, and every pass in that window billed per use. With three loops running two-to-sixteen-minute sessions on a big context, it burned through a $10 credit balance — and a bit below zero — in about twenty minutes.

Now the metered key sits in its own file, read only by the one service that needs it, with a comment right where it's used explaining why it can never move — so it's built into the setup rather than something someone has to remember, and whoever edits that config next can't really miss it.

Paying a model to find out there was nothing to do

Before there was a cheap pre-check, every pass meant waking up a full model session to read the state and decide what to do next, which was often nothing. Across roughly 3,900 daily passes, 88% were exactly that — a full, billed session whose only output was finding out the queue was empty.

The fix was kind of embarrassingly simple once I measured it: a plain check against the work queue runs first, no model involved, and only if there's real work does the loop wake a model up. What I took from it is that polling is cheap, so it should be frequent — the instinct to slow a loop down to save money is usually solving the wrong problem, when the expensive part was checking with a model instead of a plain request.

The reviewer that can't approve itself

All the agents talk to the code-hosting platform as the same shared identity, so for a while the reviewer and the builder were the same account as far as the platform was concerned — which meant the reviewer couldn't approve a pull request, because the platform correctly won't let an account approve its own work. Rather than route around that, I kept it, since a real independent approval is the one signal that can't be faked, so no role in the system can produce one on its own.

The reviewer can check things, comment and merge routine work based on its own checks, but anything a person would actually see needs a person to say yes first, in their own words. That's on purpose and staying that way.

The 21 hours I can't get back

Every collection pass writes a growing list of files, and at one point a new kind of measurement got added to what the collector writes but not to the list of files the commit step stages. The commit step didn't fail loudly — it committed the files it knew about, then tried to sync with the remote, and the sync refused because an untracked file was in the way, which stopped the whole pipeline. Twenty-one hours of real, hourly readings sat on disk and never got committed, and since the rule here is that gaps never get backfilled or interpolated, those hours are gone and show up in the record as a real gap.

The fix has two layers on purpose. Every file a collector might write is now named explicitly in the commit step, so a new one has to be added deliberately. And if something tracked still gets changed but left off the list, a fallback stages it anyway with a loud warning, rather than letting the same thing happen quietly again — belt and suspenders, basically, since the first belt already broke once and the 21 hours it cost are still sitting there in the history.

The rule underneath all of it

None of these came from an agent doing something clever and wrong — every one of them was some kind of silence: a failure with no signal, a gap nothing was watching, or an assumption nobody went back and checked. So the rule across the whole system is less about making agents smarter and more mechanical than that: nothing gets published unless it traces back to a file that was actually collected, and failed attempts stay visible. In practice that means a number that can't be traced to a real collected row doesn't ship, a source that doesn't respond gets recorded as failed publicly rather than quietly dropped from the average, and an agent that can't proceed is expected to say so and stop rather than improvise around the gap.

From a product point of view, I think that's really what the site is claiming — not that agents can be trusted to run something real unsupervised, more that you can build it so it doesn't really matter whether they can, because when something does break, and it will, it's loud, visible and traceable back to a real file.

I've left out the ops details on purpose — the server, where credentials live, key names — same as the rest of the site, and every incident above is real and was checked against this project's own commits and internal docs before publishing rather than written from memory. How it works has the collection method, and the raw code and history have everything else.
